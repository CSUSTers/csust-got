# Go 1.27 与 Paimon JSON 后端迁移设计

- 日期: 2026-09-01
- 状态: 已批准，待实施
- 分支: `feat/go1.27-paimon`
- 范围: Go 模块、JSON 后端、测试与基准、CI、Docker、开发环境和活跃文档
- 关联代码: `go.mod`、`go.sum`、`chatv2/`、`Dockerfile`、`.github/workflows/`、`.travis.yml`、`.golangci.yaml`、`.devcontainer/devcontainer.json`

## 1. 背景

项目当前声明 Go 1.26，并在 Docker、GitHub Actions、Travis、golangci-lint 和文档中分别固定或描述 Go 1.26。开发机已运行 Go 1.27.0，因此当前 CI、开发环境与生产镜像可能使用不同工具链。

`github.com/bytedance/sonic v1.15.0` 由 Eino、Eino MCP、Eino OpenAI ACL 和 `go-openai` 间接引入。Sonic v1.15.x 在 Go 1.27 下不启用其 native/JIT 实现，而是回退到标准库 JSON；Go 1.26 Docker 镜像仍可能运行 native/JIT。该差异使同一提交在开发、CI 和生产中具有不同的 JSON 实现及性能特征。

`github.com/hugefiver/paimon-go v0.1.0` 是 Go 1.27 的纯 Go Sonic 公共 API 兼容实现。其 `go.mod` 声明 `module github.com/bytedance/sonic`，因此可以作为远程 replacement 保持所有上游 import 不变。

## 2. 已确认决策

1. 整个项目和活跃基础设施统一迁移至 Go 1.27。
2. 主模块声明 `go 1.27.0`，CI 和镜像跟随 Go 1.27 的补丁版本，不自动跨到 Go 1.28。
3. 使用已发布 tag `github.com/hugefiver/paimon-go v0.1.0`，不依赖未发布的 `master`。
4. 使用模块 replacement，不维护 Eino 或其他上游依赖的 fork。
5. 显式要求 Sonic v1.15.2，作为 Paimon 声明兼容的 API 基线。
6. 不通过 `exclude` 强行删除 `sonic/loader` 的模块图记录；验收实际构建依赖不包含 loader 代码。
7. 功能兼容以项目真实 Eino 载荷的语义结果为准，不要求错误文本、map key 字节顺序或 native/JIT 行为一致。
8. Paimon 相对 Sonic native 慢 3–5 倍可以接受，但必须有自动化性能门禁和可复现 benchmark。
9. 历史 design/plan 文档不回写 Go 版本；只更新当前开发和使用文档。
10. 现有 32 位 chatv2 stub 本次不移除；仅修正把限制归因于 Sonic 的过时说明。

## 3. 目标

- 所有活跃构建、测试、lint、容器和开发环境明确使用 Go 1.27。
- 实际编译的 `github.com/bytedance/sonic` 包来自 Paimon v0.1.0。
- Eino message、tool call、schema 和 AST 查询在替换后保持项目所需的 JSON 语义。
- race 测试、普通测试、交叉构建和容器构建不回归。
- 自动性能门禁能阻止明显慢于允许范围的 JSON 后端回归。
- replacement 可通过单一 `go.mod` 变更快速回滚。

## 4. 非目标

- 不实现或移植 Sonic native/JIT、assembly 或 `sonic/loader`。
- 不修改 Eino、Eino MCP、Eino OpenAI ACL 或 `go-openai` 的源码。
- 不以本次迁移为由升级无关依赖。
- 不启用 Go 1.27 generic methods 或迁移至 `encoding/json/v2` API。
- 不承诺 Paimon 与 Sonic 在所有 malformed JSON 错误分类上完全一致。
- 不扩大 chatv2 的 32 位运行时支持范围。

## 5. 模块设计

`go.mod` 使用以下约束:

```go
go 1.27.0

require github.com/bytedance/sonic v1.15.2

replace github.com/bytedance/sonic => github.com/hugefiver/paimon-go v0.1.0
```

测试会直接导入 Sonic 公共 API，因此 Sonic 成为主模块的显式直接依赖。生产代码及所有上游依赖继续使用原始 import path。

Go 1.27 的 `go mod tidy` 会将当前三个 `require` block 标准化为最多两个 block。该格式变化属于工具链迁移的预期结果，不手工恢复旧布局。

验收时同时检查:

- `go list -m -json github.com/bytedance/sonic` 的 `Replace.Path` 和 `Replace.Version`。
- `go list -deps ./...` 中实际选中的 Sonic 包可编译。
- 实际依赖列表不包含 `github.com/bytedance/sonic/loader` package；模块图中保留 loader module 不构成失败。
- `go mod tidy -diff` 为空。

## 6. JSON 兼容测试设计

在 `chatv2` 中增加专用测试文件，使用与生产 Eino 依赖相同的 `github.com/bytedance/sonic` import path。

### 6.1 Replacement 身份

测试通过 `runtime/debug.ReadBuildInfo` 查找 `github.com/bytedance/sonic`，并要求 replacement 精确为:

- path: `github.com/hugefiver/paimon-go`
- version: `v0.1.0`

该检查防止删除 replacement 后因上游 Sonic 的 Go 1.27 fallback 仍能通过功能测试。

### 6.2 真实载荷兼容

覆盖以下 API 和数据:

- `Marshal` / `Unmarshal`
- `MarshalString` / `UnmarshalString`
- `Valid`
- `GetFromString` 与 AST node 读取/序列化
- Eino `schema.Message`、tool calls 和 function arguments
- JSON Schema 风格嵌套 map/slice
- `json.Marshaler` 自定义类型
- Unicode、转义字符、整数、浮点数、`json.Number` 和 `null`
- malformed/trailing JSON 的成功或失败边界

与 `encoding/json` 的差分比较以解码后的 Go 值或规范化 JSON 结构为准。测试不比较错误字符串，也不把 map key 的输出顺序作为契约。

### 6.3 项目集成

现有 chatv2 mapping、tool、MCP、agent 和 streaming 测试继续作为上层回归证据。新增测试只补足当前缺少的 JSON backend 身份与 Eino 载荷契约，不复制 Paimon 自身完整测试套件。

## 7. 性能设计

增加普通 benchmark，至少包含:

- 代表性 Eino message/tool-call payload marshal
- 同一 payload unmarshal
- nested `GetFromString`
- `Valid`

benchmark 使用 `-benchmem` 报告延迟和分配，不设置机器相关的绝对纳秒阈值。

另增加不带 race instrumentation 的自动性能测试。它在同一进程、同一 payload 上使用 `testing.Benchmark` 比较 Paimon 与 Go 1.27 `encoding/json` 的 marshal/unmarshal。每项要求:

```text
paimon ns/op <= encoding/json ns/op * 2.5
```

Paimon 当前公开数据约等于或快于 Go 1.27 标准库，而 Sonic native 在代表性操作上通常比标准库快约 1.6–2 倍。2.5 倍标准库上限对应约 4–5 倍 Sonic native 的保守最坏边界，符合已批准容忍度。

性能测试文件使用 `!race` build constraint，避免 race instrumentation 对不同实现造成不对称放大。CI 在 race suite 之外单独运行性能门禁。分配数据用于诊断，不作为硬门禁，以降低跨平台抖动导致的误报。

## 9. 验证矩阵

必须通过:

1. `go version` 为 1.27.x。
2. replacement 身份测试和模块审计。
3. JSON 兼容定向测试。
4. 非 race 性能门禁。
5. `go test -race -covermode=atomic -short ./...`。
6. `go build ./...`。
7. Linux `amd64`、`arm64`、`386`、`arm/v7` 的 `CGO_ENABLED=0` 构建。
8. `gofmt` 检查和不自动修复的 golangci-lint。
9. `go mod tidy -diff` 为空。
10. Docker 可用时执行镜像构建；不可用时明确记录未验证项。

由于 386/arm 使用既有 stub，交叉构建只证明项目可构建，不证明 chatv2 在这些平台具有完整功能。

## 10. 错误处理与回滚

- 若 Paimon 缺失 Eino 实际使用的 API，迁移失败，不通过修改上游依赖或跳过测试规避。
- 若语义差分只涉及未承诺的错误文本或 map 顺序，测试应比较结构语义；其他行为差异必须调查后决定是否可接受。
- 若性能超过 2.5 倍标准库门禁，先用 benchmark 确认具体操作，不提高阈值掩盖回归。
- 若某平台构建失败，保留失败证据并修复；不得静默删除现有构建矩阵。
- 回滚时移除 replacement 和新增后端测试/门禁，并恢复所有 Go 版本钉住点。不存在数据格式迁移或持久化回滚。
